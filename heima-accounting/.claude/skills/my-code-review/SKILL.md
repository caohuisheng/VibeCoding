# 代码审查 — 工作区未提交变更

此技能对 `git diff HEAD` 中所有未提交的变更进行系统化代码审查，覆盖 Rust 后端（src-tauri/）和 TypeScript/React 前端（src/）。

## 执行流程

### 第一步：确定审查范围

```bash
# 获取变更文件列表
git diff HEAD --name-only

# 获取未跟踪文件
git ls-files --others --exclude-standard
```

将文件和变更内容按以下分类：
| 类别 | 文件后缀 | 审查重点 |
|------|---------|---------|
| Rust 后端 | `.rs` | 内存安全、错误处理、SQL 注入、并发安全 |
| TypeScript/React | `.ts`, `.tsx` | 类型安全、React 最佳实践、状态管理、性能 |
| 配置/样式 | `.json`, `.css`, `.toml` | 配置正确性、格式规范 |
| 文档 | `.md`, `.txt` | 内容完整性、格式 |

### 第二步：逐文件获取变更

对每个变更文件，执行：
```bash
git diff HEAD -- <文件路径>
```

如果是新文件，使用：
```bash
cat <文件路径>
```

### 第三步：按维度审查

对每个变更文件，从以下维度逐项审查。每个维度发现的问题记录为一条发现，包含：**文件**、**行号**、**严重级别**（🔴严重 / 🟡警告 / 🔵建议）、**问题描述**、**修复建议**。

---

## 审查维度

### 维度 1：正确性（Correctness）

检查代码是否可能导致错误、崩溃或意外行为。

**Rust 后端：**
- [ ] `.unwrap()` / `.expect()` 是否可能在运行时 panic？（重点关注：锁获取、数据库操作、用户输入解析）
- [ ] 错误传播是否完整？是否存在吞掉错误的情况（如 `let _ = fallible_fn()`）？
- [ ] `unsafe` 代码块是否存在？是否必要？是否正确？
- [ ] 整数溢出、浮点精度问题（金额计算用 `f64` 是否合适？）
- [ ] 日期/时间处理是否正确？（时区、格式、边界条件如月末）
- [ ] SQL 查询逻辑是否正确？JOIN 条件是否完整？
- [ ] 并发访问是否存在竞态条件？（Mutex 毒化、死锁）

**TypeScript/React 前端：**
- [ ] `any` 类型使用是否合理？是否可以替换为具体类型？
- [ ] 类型断言 (`as`, `!`) 是否有安全风险？
- [ ] 可选链 (`?.`) 和空值合并 (`??`) 使用是否正确？
- [ ] 异步操作是否正确处理 loading / error / empty 状态？
- [ ] 数组/对象访问前是否做了空值检查？
- [ ] 日期格式化、金额格式化边界情况是否正确？
- [ ] 条件渲染逻辑是否覆盖所有分支？

### 维度 2：安全性（Security）

**Rust 后端（SQLite + Tauri）：**
- [ ] SQL 查询是否使用参数化？是否存在字符串拼接构造 SQL？
  - ✅ 安全：`params![value]`、`rusqlite::params_from_iter()`
  - ❌ 危险：`format!("SELECT ... {} ", user_input)`
- [ ] 用户输入是否经过验证/清理？
- [ ] 敏感数据（如数据库路径）是否妥善处理？
- [ ] Tauri 命令权限是否正确配置？是否有暴露过多系统能力的风险？
- [ ] CSV 导出是否存在注入风险？（公式注入 `=`, `+`, `-`, `@` 开头的内容）

**TypeScript/React 前端：**
- [ ] 是否存在 XSS 风险？（`dangerouslySetInnerHTML`、直接操作 DOM）
- [ ] API 调用是否验证返回数据？
- [ ] 敏感信息是否被硬编码？（密钥、token、密码）
- [ ] 本地存储的数据是否包含敏感信息？

### 维度 3：性能（Performance）

**Rust 后端：**
- [ ] 数据库查询是否有合适的索引？
- [ ] N+1 查询问题：循环中是否执行了数据库查询？
- [ ] 不必要的数据克隆（`.clone()`）是否可以改为借用？
- [ ] 集合操作是否选用了合适的数据结构？
- [ ] Mutex 持有时间是否过长？（锁范围内是否有 I/O 或重计算？）

**TypeScript/React 前端：**
- [ ] 是否存在不必要的重新渲染？`useMemo` / `useCallback` / `React.memo` 是否合理使用？
- [ ] 列表渲染是否有稳定的 `key`？
- [ ] 大数据量列表是否考虑虚拟滚动？
- [ ] 图表数据计算是否放在 `useMemo` 中？
- [ ] 是否在 `useEffect` 中存在不必要的依赖导致无限循环？
- [ ] ECharts 实例是否正确销毁（`dispose`）防止内存泄漏？

### 维度 4：代码风格与可维护性（Style & Maintainability）

- [ ] 命名是否清晰、符合项目惯例？
  - Rust: `snake_case` 函数/变量，`CamelCase` 结构体/枚举，`SCREAMING_SNAKE_CASE` 常量
  - TypeScript: `camelCase` 函数/变量，`PascalCase` 组件/类型，`UPPER_CASE` 常量
- [ ] 函数是否过长（超过 50 行建议拆分）？
- [ ] 是否存在重复代码？是否可以提取为公共函数？
- [ ] 注释是否必要的？是否解释了"为什么"而非"是什么"？
- [ ] 错误消息是否对用户友好？
- [ ] TODO/FIXME/HACK 标记是否需要跟踪？
- [ ] 是否有未使用的导入或变量？

### 维度 5：测试（Testing）

> 提示：如果涉及 `src-tauri/` 变更，可建议用 `/unit-test` 验证。

- [ ] 新增/修改的功能逻辑是否需要更新测试？
- [ ] 边界情况是否被覆盖？
- [ ] 是否有遗漏的测试场景？（空输入、极值、并发、错误路径）

## 输出格式

审查完成后，按以下格式汇总：

```markdown
## 📋 代码审查报告

**审查范围**：N 个文件，M 行变更
**审查时间**：YYYY-MM-DD

### 总览

| 严重级别 | 数量 |
|---------|------|
| 🔴 严重 | X |
| 🟡 警告 | Y |
| 🔵 建议 | Z |

### 逐文件发现

#### 📄 path/to/file1.rs

| # | 级别 | 行号 | 问题 | 建议 |
|---|------|------|------|------|
| 1 | 🔴 严重 | 42 | `unwrap()` 可能 panic | 改用 `map_err(|e| e.to_string())?` |
| 2 | 🟡 警告 | 58 | 变量命名不够清晰 | 建议重命名为 `bill_list` |

#### 📄 path/to/file2.tsx

| # | 级别 | 行号 | 问题 | 建议 |
|---|------|------|------|------|
| 1 | 🔵 建议 | 15 | `useEffect` 缺少依赖项 | 添加 `[userId]` 到依赖数组 |

### 总体评价

<一段简短的整体评价，包括代码质量的总体印象和最大的风险点>
```

## 注意事项

1. **只审查变更部分**：聚焦 `git diff` 的实际改动，不审查未变更的已有代码（除非变更引入的上下文依赖值得提及）。
2. **给出具体建议**：每个问题都要附上具体的修复建议，最好包含代码示例。
3. **不做无意义的挑剔**：如果代码风格符合项目惯例，即使不符合个人偏好也不提。
4. **区分严重级别**：
   - 🔴 严重：会导致崩溃、数据丢失、安全漏洞、功能异常，必须在合入前修复
   - 🟡 警告：潜在风险、性能问题、不符合最佳实践，建议修复
   - 🔵 建议：代码改进、命名优化、注释补充，可后续优化
5. **关注项目规则**：遵循 CLAUDE.md 中定义的规则（如金额单位人民币、数据本地存储等）。
6. **审查深度自适应**：
   - 1-3 个文件变更：逐行详细审查
   - 4-10 个文件变更：重点审查关键逻辑
   - 10+ 个文件变更：按模块概要审查，标注重点问题

## 与前端的协同审查

本技能主要审查代码变更。如果发现需要视觉验证的问题（UI 布局、交互逻辑），建议用户运行 `/run-app` 启动应用进行人工验收。
